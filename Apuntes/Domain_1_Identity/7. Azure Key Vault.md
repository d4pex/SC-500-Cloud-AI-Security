El principio fundamental: Nunca, bajo ninguna circunstancia, se deben guardar contraseñas, claves o cadenas de conexión en el código fuente ni en archivos de configuración. Para eso existe Key Vault.

1.Tipos de Bóveda: Standard Key Vault vs. Managed HSM
El examen suele poner trampas sobre cuál elegir.
* Azure Key Vault (Standard o Premium): Es como la caja fuerte de una habitación de hotel. Un servicio multitenant compartido. La versión Premium ofrece claves respaldadas por hardware (HSM) FIPS 140-2 Level 3. Esta es la respuesta correcta para el 95% de los escenarios.
* Azure Managed HSM: Es como la bóveda de un banco real. Es un entorno de inquilino único (Single Tenant), certificado FIPS 140-3 Level 3, y ni siquiera Microsoft tiene acceso a él. Solo debes elegir esta opción si el escenario menciona explícitamente "Single Tenant", "FIPS 140-3" o "Cumplimiento normativo estricto/Gobierno".

2.Permisos: Access Policies vs. Azure RBAC
* Access Policies (El modelo antiguo): Un sistema de permisos aislado que solo existía dentro de Key Vault. No se integraba bien con el resto de Azure. Ya no se recomienda.
* Azure RBAC (El modelo moderno): Es el estándar actual. Utiliza los roles de Azure para dar permisos sobre el Plano de Datos (Data Plane).
* Roles RBAC Clave para memorizar:
	* Key Vault Administrator: Acceso total al plano de datos.
	* Key Vault Secrets Officer: Puede crear, modificar y borrar secretos.
	* Key Vault Secrets User: Solo puede leer el valor de los secretos (Ideal para aplicaciones).

3.El Patrón "Canónico" de Acceso a Secretos (¡Pregunta de examen 100% segura!)
Si te preguntan cómo una aplicación web (App Service) debe acceder a una base de datos sin guardar credenciales, el orden exacto de los pasos (Drag & Drop) es:
* Habilitar una Managed Identity (Identidad Administrada) en el App Service.
* Asignar el rol de Key Vault Secrets User a esa Managed Identity en el Key Vault.
* Guardar la contraseña en el Key Vault.
* Configurar el App Service para que use un Key Vault Reference apuntando a la URI del secreto.

4.Protección contra borrados accidentales (y maliciosos)
* Soft Delete: Es la papelera de reciclaje. Viene activada por defecto y no se puede apagar. Retiene los secretos/bóvedas borrados entre 7 y 90 días.
* Purge Protection (Protección de purga): Es el candado de la papelera. Una vez activado, es irreversible. Impide que nadie (ni siquiera un Administrador Global) pueda forzar el borrado definitivo ("purga") de un secreto antes de que expire el tiempo de retención del Soft Delete. Esencial para evitar sabotajes internos o ransomware.

5.Aislamiento de Red
Para que un Key Vault sea seguro en producción, necesita el trío de aislamiento de red:
* Crear un Private Endpoint (Punto de conexión privado).
* Vincular una Private DNS Zone.
* Desactivar el acceso a la red pública (Disable public network access) en el firewall del Key Vault. (Si haces los dos primeros y te olvidas de este tercero, tu bóveda sigue expuesta a internet).

6.Rotación y Customer Managed Keys (CMK)
* Puedes usar las claves criptográficas del Key Vault para cifrar discos (Disk Encryption) o bases de datos y Storage Accounts (Transparent Data Encryption).
* Si la organización quiere tener el control absoluto de sus claves de cifrado en lugar de depender de Microsoft, esto se llama Customer Managed Keys (CMK).

7.Defender for Key Vault
* Se activa a nivel de Suscripción dentro de Defender for Cloud.
* Sirve para detectar accesos anómalos en el plano de datos (ej. un usuario listando claves desde una IP en un país inusual). No detecta cambios en el plano de control (ej. asignar un rol), para eso necesitas revisar el Activity Log en Sentinel.
