Las cuentas de almacenamiento son las "cajas fuertes" donde guardas blobs, archivos, colas y tablas. La seguridad se construye en capas: red (el suelo), identidad (el techo) y encriptación.

1.Tipos de Cuentas y Acceso Público
* General Purpose v2 (GPv2): Es el tipo de cuenta por defecto y el correcto para el 99% de los casos.
* Data Lake Storage Gen2: Se habilita marcando la casilla "Hierarchical namespace" al crear una GPv2. Importante: Esta es la única forma de habilitar Listas de Control de Acceso (ACLs) estilo POSIX para carpetas y archivos individuales.
* Red y Firewall: Por defecto, las cuentas nacen públicas. El patrón seguro es configurarlo en Disabled (desactivado) y acceder solo a través de Private Endpoints.
* Excepción del Firewall: Si activas el firewall de almacenamiento, debes marcar obligatoriamente la casilla "Allow Azure services on the trusted services list", de lo contrario bloquearás incluso al portal de Azure y otras herramientas internas.

2.Shared Access Signatures (SAS Tokens)
Un SAS es como un "pase de backstage temporal". Te da acceso por un tiempo limitado a ciertos recursos. Tienes que saber diferenciar los tres tipos:
* Account SAS: Muy peligroso. Se firma con la clave maestra de la cuenta. Da acceso a múltiples servicios (blob, file, queue). Si se filtra, es un desastre.
* Service SAS: Un poco más seguro. Se firma con la clave de la cuenta pero se restringe a un solo servicio o contenedor.
* User Delegation SAS (¡LA RESPUESTA CORRECTA!): El estándar de oro. No usa las claves compartidas. Se firma con un token temporal de Entra ID. Esto permite auditar quién lo generó exactamente. Si la cuenta de Entra se bloquea, el SAS muere con ella. En el examen, si te dan a elegir, elige siempre User Delegation SAS.

3.El problema de Revocar un SAS (Stored Access Policies)
* Una vez generas un SAS normal (Account/Service), no puedes revocarlo individualmente. La única forma de matarlo es rotar (cambiar) la clave maestra de la cuenta, lo que rompería todas las demás aplicaciones que usen esa clave.
* La solución: Stored Access Policies. Creas una política en el contenedor y vinculas tu SAS a esa política. Si necesitas revocar el acceso a alguien, simplemente borras la política y el SAS vinculado muere instantáneamente, sin afectar a nadie más.

4.La Acción de Mayor Impacto: Deshabilitar Shared Key Access
* Por defecto, las Storage Accounts permiten el acceso usando una de las dos claves maestras (Access Keys). Cualquier persona o aplicación con la clave tiene control absoluto sobre los datos.
* Mejor práctica: Debes ir a la configuración y poner "Allow storage account key access" en FALSE (Deshabilitado).
* Al hacer esto, fuerzas a que toda conexión deba usar Microsoft Entra ID (RBAC) para autenticarse, lo que permite control granular y auditoría.
* Cuidado: Antes de apagarlo, revisa los logs para asegurarte de que ninguna aplicación legacy dependa de esas claves.

5.El "Gold Standard" (Configuración a memorizar)
Si el examen te muestra una cuenta mal configurada y te pide arreglarla, debes buscar estas configuraciones:
* Account Type: General Purpose v2.
* Public Network Access: Disabled (Solo Private Endpoints).
* Allow Blob Anonymous Access: Disabled.
* Shared Key Access: Disabled (Forzar Entra ID).
* Customer Managed Key (CMK): Activado, apuntando a un Key Vault que obligatoriamente debe tener Purge Protection activado.
* Soft Delete / Versioning: Activado para recuperar borrados accidentales.
