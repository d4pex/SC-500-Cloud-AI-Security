Asegurar los permisos de un recurso no sirve de mucho si su "puerta principal" sigue expuesta al internet público. Este capítulo trata sobre cómo ocultar esa puerta dentro de tu propia red privada.

1.Las 3 Formas de Conectar a un Recurso (Ej. Storage o SQL)
* Public Access protegido por Firewall: La IP sigue siendo pública, pero creas una lista blanca de qué IPs pueden entrar. (Como un portero de discoteca con una lista de invitados en la calle).
* Service Endpoint: El tráfico desde tu VNet hacia el recurso viaja por la red interna de Azure (Microsoft backbone) y no por internet. Es gratis y fácil, pero el recurso sigue teniendo una IP pública.
* Private Endpoint (El Gold Standard): Literalmente coloca una tarjeta de red virtual (NIC) dentro de tu propia subred y le asigna una IP privada de tu rango (Ej. 10.0.0.5). El recurso ya no responde a internet, es un habitante más de tu red. Esta es la respuesta correcta en casi cualquier escenario del SC-500 que mencione "Zero Trust" o "Regulaciones".

2.La Trampa del DNS (¡PREGUNTA DE EXAMEN SEGURA!)
* Cuando creas un Private Endpoint, tu aplicación sigue intentando conectar a la misma URL de siempre (ej. midatabase.database.windows.net).
* Si tu aplicación hace una resolución DNS normal, el sistema le devolverá la IP Pública antigua, intentará ir por internet y fallará.
* La Solución Obligatoria: Necesitas un Private DNS Zone. Debes crear una zona DNS privada (ej. privatelink.database.windows.net), vincularla a tu VNet, y hacer que apunte a tu IP privada.
* Escenario típico: "He creado un Private Endpoint pero el tráfico sigue yendo por la IP pública, ¿qué falta?". Respuesta: Vincular el Private DNS Zone a la Virtual Network (VNet link).

3.Sub-recursos (Subresources)
* Un solo recurso de Azure puede necesitar múltiples Private Endpoints.
* Ejemplo: Una Storage Account necesita un Private Endpoint para "Blob", otro diferente para "File", otro para "Table" y otro para "Queue". Cada uno necesita su propio registro DNS.

4.Azure Private Link Service (Cuando tú eres el que vende el software)
* Private Endpoint es para consumir un servicio.
* Private Link Service es para publicar/ofrecer un servicio.
* Si tu empresa crea una aplicación y se la vende a otros clientes en Azure, puedes poner un Private Link Service detrás de un Load Balancer. Esto permite que los clientes creen Private Endpoints en sus propias VNets para consumir tu aplicación sin pasar por internet.

5.Microsoft Entra Private Access (El Asesino de las VPN)
* Legacy VPN: El usuario se loguea una vez y la VPN le da una "tubería" gigante que le permite ver toda la red de la empresa. Si el PC del usuario tiene malware, el malware entra a la red.
* Entra Private Access: Es la versión Zero Trust de Microsoft (parte de Global Secure Access).
	* No hay una "tubería" gigante. El acceso es App por App.
	* No hay que abrir puertos entrantes en tu firewall local (inbound). Instalas un conector ligero dentro de tu red que solo hace conexiones de salida (outbound) hacia Microsoft.
	* Lo más importante: Permite aplicar Políticas de Acceso Condicional (Conditional Access) al tráfico de red tradicional (como RDP, SMB o SSH). Puedes requerir MFA para abrir un escritorio remoto local.

6.El Patrón Canónico de Cierre (Configuración Perfecta)
Si el examen te pide asegurar un recurso de red, este es el orden de acciones:
* Deshabilitar el acceso público (Disable public network access) en el recurso. (Cuidado: Crear un private endpoint no cierra el público automáticamente).
* Crear el Private Endpoint en la subred elegida.
* Crear y vincular el Private DNS Zone correcto para ese servicio.
* (Opcional pero crítico en entornos híbridos): Configurar un Azure DNS Resolver si las máquinas locales (On-Premises) también necesitan resolver esa dirección privada a través del túnel VPN/ExpressRoute.
