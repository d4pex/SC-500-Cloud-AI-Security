Proteger aplicaciones PaaS (Platform as a Service) es diferente a proteger máquinas virtuales. No hay sistema operativo que parchear; la seguridad se basa en la identidad, la red y la configuración de la plataforma.

1.App Service Authentication (Easy Auth)
No escribas código de autenticación (login, validación de tokens, redirecciones) dentro de tu aplicación si puedes evitarlo.
* Easy Auth: Es un "Sidecar" (proceso paralelo) que intercepta el tráfico antes de que llegue a tu código. Tú le dices qué proveedor usar (Entra ID, Google, etc.) y él se encarga de todo.
* Configuración Clave: Debes configurarlo en "Require authentication" (Requerir autenticación). Si por error lo dejas en "Allow unauthenticated access", la app estará completamente abierta a internet y tu código recibirá tráfico no validado (Típica trampa de examen).

2.El "Trío Canónico" de Seguridad PaaS (¡MEMORIZAR!)
Si un caso de estudio te pide asegurar una aplicación web que se conecta a una base de datos sin guardar contraseñas y sin exponerse a internet, la respuesta SIEMPRE es la combinación de estas tres cosas:
* Managed Identity (Identidad Administrada): Activada en el App Service.
* Key Vault References: El App Service usa esta sintaxis especial en sus ajustes para leer el secreto de Key Vault usando su Managed Identity, sin guardar texto plano.
* Private Endpoint: Oculta el Key Vault y la Base de Datos para que solo respondan a IPs privadas de tu VNet.

3.Aislamiento de Red en App Service (Inbound vs. Outbound)
Tienes que diferenciar hacia dónde va el tráfico para elegir la herramienta correcta:
* VNet Integration (Integración de red virtual): Es para el tráfico Outbound (de salida). Permite que tu App Service pueda "entrar" a tu red virtual para hablar con bases de datos internas o recursos On-Premise.
* Private Endpoint: Es para el tráfico Inbound (de entrada). Le da a tu App Service una IP privada para que los empleados puedan acceder a la web sin pasar por la IP pública.
* App Service Environment (ASE): (Cómputo Single-Tenant). Es muy caro y tardado de provisionar. Solo se elige cuando la pregunta dice: "Regulación extrema que prohíbe compartir hardware físico con otros clientes de Azure".

4.Defender for App Service
Actúa de dos formas (ambas sin tocar tu código):
* Runtime Protection: Detecta cosas como ejecución de comandos sospechosos, procesos hijos anómalos o comportamientos que indican un Web Shell.
* Dangling DNS (DNS Colgante): Si borras tu App Service pero olvidas borrar el registro CNAME en tu proveedor de DNS, un atacante podría crear un nuevo App Service reclamando tu nombre antiguo. Defender te avisa de esto.

5.Azure Functions y Logic Apps
* Comparten exactamente la misma arquitectura base que App Service.
* Tip de seguridad: Deshabilita el uso de "Function Keys" (claves en texto plano compartidas) y usa siempre Managed Identities y autenticación de Entra ID para proteger el acceso a las funciones.

6.API Management (APIM)
Si tienes muchas APIs, APIM actúa como la puerta principal.
* Centraliza la validación de tokens OAUTH y JWT (JSON Web Tokens).
* Trampa de examen: Al configurar la política de validación JWT en APIM, no basta con validar la firma; SIEMPRE debes validar el claim audience (aud) para asegurarte de que el token fue emitido específicamente para tu API y no robado de otra aplicación.

7.Front Door + WAF (La Arquitectura Moderna)
La arquitectura perfecta para una web pública consta de:
* Azure Front Door: (Balanceador global) con WAF (Web Application Firewall) para parar inyecciones SQL y ataques en el borde (Edge).
* App Service: Detrás de Front Door.
* Restricción de Acceso (Access Restriction): Para evitar que alguien se salte Front Door y ataque directamente al App Service, debes bloquear el App Service permitiendo solo el Service Tag AzureFrontDoor.Backend Y ADEMÁS verificar el valor del header X-Azure-FDID (para asegurar que es tu Front Door y no el de otro cliente de Azure).
