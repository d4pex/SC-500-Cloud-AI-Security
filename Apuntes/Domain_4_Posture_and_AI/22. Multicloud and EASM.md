Defender for Cloud actúa como un panel centralizado de seguridad (CSPM y Workload Protection) para tus recursos de Azure, AWS y Google Cloud (GCP). Todo termina en el mismo Secure Score y en el mismo mapa de rutas de ataque.

1.Conectar AWS a Defender for Cloud
* ¿Cómo se conecta? Utiliza un script de CloudFormation (la versión de AWS de las plantillas ARM de Azure) generado automáticamente.
* El Modelo de Identidad (Sin contraseñas): Crea un rol (IAM Role) en AWS. En lugar de darle una contraseña a Microsoft, se configura una Política de Confianza (Trust Policy). AWS confía en que una cuenta específica de Microsoft asuma ese rol.
* External Identifier (Identificador Externo): ¡Ojo al dato! Para evitar que otro cliente de Microsoft se haga pasar por ti, la conexión exige un ID externo único vinculado a tu tenant de Azure. Si alguna vez lo rotas/cambias, la conexión se rompe hasta que lo actualices en AWS.
* Mejor práctica: Conecta siempre la cuenta "Management" (raíz) de la organización AWS para que todas las subcuentas se agreguen solas.

2.Conectar GCP (Google Cloud) a Defender for Cloud
* El problema antiguo: Antes se generaba un archivo de claves estático (Service Account Key File), que los desarrolladores solían perder o subir por error a GitHub.
* La solución actual (Workload Identity Federation): GCP ya no necesita claves largas. Confía en Entra ID como proveedor de identidad. Defender for Cloud le pide tokens de corta duración (short-lived tokens) a GCP en el momento de leer los datos.

3.¿Qué planes de Defender funcionan fuera de Azure?
Esta es una pregunta clásica de opción múltiple. No todos los planes sirven para todo.
* Planes que SÍ funcionan en AWS y GCP:
	* Defender for Servers (Máquinas virtuales, EC2, Compute Engine).
	* Defender for Containers (EKS en AWS, GKE en GCP).
	* Defender for Databases (RDS, Cloud SQL).
* Planes que son SOLO para Azure:
	* Defender for Storage (AWS S3 y GCP Buckets usan un modelo diferente).
	* Defender for App Service.
	* Defender for Key Vault.
	* Defender for APIs.

4.EASM (External Attack Surface Management) - El "Hacker Ético Automático"
* CSPM normal: Mira tu casa desde dentro (ej. "Ese servidor no tiene un parche").
* EASM: Mira tu casa desde fuera, exactamente como lo haría un atacante escaneando Internet.
* ¿Cómo funciona? Le das "Semillas" (Seeds). Por ejemplo, tu dominio kintoso.com o tus bloques de IPs públicas.
* EASM rastrea como una araña (spidering): busca subdominios ocultos (dev.kintoso.com), analiza certificados SSL expirados, descubre servidores web olvidados en AWS que usan tu marca, y detecta IPs que se conectan a bases de datos directamente desde internet.
* Integración: EASM no es una herramienta aislada. Sus descubrimientos se integran en Defender CSPM, afectando directamente a tu Secure Score y completando el grafo de "Attack Path Analysis" con la entrada pública real del ataque.
